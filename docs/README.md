**Tennis Match Scoreboard** — это веб-приложение для ведения счёта теннисных матчей в реальном времени с сохранением 
результатов в базу данных. Проект реализован на классическом Java-стеке без использования тяжеловесных
фреймворков (Spring) с целью глубокого понимания архитектурных паттернов, спецификации Jakarta Servlet и
работы ORM Hibernate.

## 🚀 Быстрый старт

### Предварительные требования
Перед запуском убедитесь, что у вас установлены:
* **Java 21** (или выше)
* **Maven** (для сборки проекта)
* **Tomcat 11** (сервер приложений)
* **Redis** (запущенный локально на стандартном порту `6379`)

### Пошаговая инструкция по запуску

#### Шаг 1: Подготовка инфраструктуры
1. Убедитесь, что ваш **Redis** запущен и доступен по адресу `localhost:6379`.
2. **Важная настройка для Tomcat:** Для корректной обработки HTTP-методов проверьте конфигурационный файл
`{путь_к_Tomcat}/conf/server.xml`. Укажите параметр `parseBodyMethods` внутри тега `<Connector>`, 
иначе Tomcat может игнорировать тела запросов для некоторых методов:

```xml
<Connector port="8080" protocol="HTTP/1.1"
connectionTimeout="20000"
redirectPort="8443"
parseBodyMethods="POST,PUT,PATCH" />
```

#### Шаг 2: Сборка приложения
Склонируйте репозиторий и соберите .war архив с помощью Maven:

```Bash
mvn clean package
```

После успешной сборки в директории `target/` появится скомпилированный артефакт.

#### Шаг 3: Деплой и запуск
Скопируйте полученный файл `target/tennis-scoreboard-1.0.war` в папку `webapps/` вашего установленного Tomcat 11.

Запустите Tomcat с помощью скрипта:

Windows: 
```{путь_к_Tomcat}/bin/startup.bat```

Linux/macOS: 
```{путь_к_Tomcat}/bin/startup.sh```

#### Шаг 4: Проверка работы

Приложение инициализирует подключения к Redis и Hibernate в момент старта контейнера. Чтобы убедиться,
что все контексты поднялись без ошибок, вы можете проверить логи:
* **В консоли:** Вывод дублируется в терминал запущенного Tomcat `STDOUT`.
* **В файле:** В рабочей директории запущенного сервера автоматически создастся файл `logs/project.log`.

Ожидаемый путь: `{путь_к_Tomcat}/bin/logs/project.log`

После того как веб-контейнер распакует архив, приложение будет доступно в браузере по адресу:

> 👉 http://localhost:8080/tennis-scoreboard-1.0

## 🔄 Функционал приложения

**Создание матча (`/new-match`):** форма ввода уникальных имён двух игроков. Автоматически проверяет наличие
игроков в БД (и создает новых при необходимости), генерирует уникальный `UUID` матча и инициализирует счёт.

**Интерактивное табло (`/match-score?uuid=`):** реализована система подсчёта очков в теннисе 
(0, 15, 30, 40, ровно/больше-меньше).
   * Матчи играются в формате *Best of 3* (до 2 выигранных сетов).
   * При счёте 6/6 по геймам в сете разыгрывается *тай-брейк* до 7 очков.

**Архив матчей (`/matches`):** 
постраничный просмотр (пагинация) всех завершенных игр с возможностью 
фильтрации и поиска по паттерну имени и фильтрации по количеству отображаемых матчей.

## ⚙️ Технологический стек
* **Сборка**: Maven 3.9.6
* **Backend:** Java 21, Jakarta Servlet API 6.1, Apache Tomcat 11 (Сервлет-контейнер), JSP / JSTL
* **Data & Persistence:** Hibernate 6.5 + пул соединений HikariCP, H2 Database (In-Memory), Redis (Jedis 7.4) 
для хранения текущих матчей

Logback + SLF4J (логирование: вывод в консоль + запись в файл), JUnit5 (модульное тестирование)
* **Frontend:** HTML/CSS вёрстка
> **Примечание:** файл `style.css` был реализован с помощью ИИ-инструмента!

## 📂 Архитектура и структура проекта

Приложение спроектировано по принципам многослойной архитектуры с выраженным разделением ответственности
и использованием паттерна **MVCS (Model-View-Controller-Service)**, а также элементов **DDD (Domain-Driven Design)** 
для изоляции правил теннисного счёта.

### Ключевые архитектурные решения

**Разделение домена (domain) и реляционных сущностей (entity):**

* Папка entity содержит «анемичные» модели, которые нужны только для Hibernate и отражают структуру таблиц базы данных.

* Папка domain содержит «богатую» доменную модель. Классы TennisMatch, TennisSet, а также реализации интерфейса 
GameMode содержат в себе состояние и позволяют его изолированно регулировать.

**Гибридная система хранения:**

* Текущие матчи требуют высокой скорости чтения/записи и частых обновлений счета. 
Они хранятся в оперативной памяти Redis в виде JSON-строк.

* Завершенные матчи требуют долгосрочного хранения и реляционных связей. Они сохраняются в СУБД H2 через
классический паттерн DAO с использованием Hibernate.

**Ручное внедрение зависимостей:**

* Инициализация проекта (создание SessionFactory, RedisClient), репозиториев и сервисов
происходит централизованно в AppContextListener при старте веб-контейнера.

* Зависимости внедряются строго через конструкторы, что гарантирует неизменяемость. 
Готовые синглтоны сервисов кладутся в ServletContext.

## 📊 Структура Базы Данных

Поскольку используется база данных *In-Memory*, схемы таблиц и заполнение данными инициализируются автоматически
при каждом запуске приложения из JPA-моделей и SQL-скрипта.

### Таблица `Players` (Игроки)

| Столбец  | Тип данных  | Ограничения        | Описание                        |
|:---------|:------------|:-------------------|:--------------------------------|
| **ID**   | INT         | PK, Auto-Increment | Уникальный идентификатор игрока |
| **NAME** | VARCHAR(40) | UNIQUE, NOT NULL   | Имя или никнейм теннисиста      |

### Таблица `Matches` (Завершенные матчи)

| Столбец           | Тип данных | Ограничения                    | Описание                       |
|:------------------|:-----------|:-------------------------------|:-------------------------------|
| **ID**            | INT        | PK, Auto-Increment             | Уникальный идентификатор матча |
| **FIRST_PLAYER**  | INT        | FK ➡️ `Players(ID)`, NOT NULL  | Ссылка на первого игрока       |
| **SECOND_PLAYER** | INT        | FK ➡️ `Players(ID)`, NOT NULL  | Ссылка на второго игрока       |
| **WINNER**        | INT        | FK ➡️ `Players(ID)`, NOT NULL  | Ссылка на победителя матча     |

> 🛡️ **Валидация на уровне СУБД (CHECK):** > В базу невозможно записать некорректный матч благодаря ограничению
`FIRST_PLAYER <> SECOND_PLAYER AND (WINNER = FIRST_PLAYER OR WINNER = SECOND_PLAYER)`. Оно гарантирует, 
что соперники уникальны, а выиграть может только участник матча.

## 🧪 Тестирование

Корректность расчета очков и переключения игровых режимов покрыта модульными тестами с использованием **JUnit 5**. 
Протестированы критические теннисные кейсы:

### Логика классического гейма (DefaultGameTest)

* **Правило Deuce (Ровно):** Проверена корректность перехода игрока в состояние ADVANTAGE (Преимущество) 
при розыгрыше мяча со счета 40:40.

* **Взятие гейма со счета 40:0:** Проверка фиксации победы в гейме при успешном розыгрыше с явным преимуществом.

* **Закрытие гейма из Advantage:** Подтверждение победы в гейме, если очко берет игрок, уже владеющий преимуществом.

### Режим тай-брейка (TieBreakGameTest)
* **Отсутствие перевеса:** Проверка продолжения игры при счете 7:7, так как ни один из игроков не 
достиг необходимого отрыва в 2 очка.

* **Быстрая победа:** Фиксация выигрыша тай-брейка при достижении 7 очков с разрывом более двух очков 
(кейсы со счетом 7:0 и 7:5).

* **Затяжной тай-брейк:** Проверка победы при игре выше минимального счёта (кейс перехода со счета 8:7 к финальным 9:7).

### Логика теннисного сета (TennisSetTest)
* **Автоматическая активация тай-брейка:** Проверка переключения сета в режим TieBreakGame, как только счет по геймам
становится 6:6.

* **Классическое завершение сета:** Фиксация победы в сете при стандартном счете (переход с 5:4 по геймам к победным 6:4).

* **Завершение сета через тай-брейк:** Фиксация победы в сете со счетом 7:6 после успешного окончания тай-брейка.

* **Сброс игрового режима:** Проверка того, что после победы на тай-брейке игровой режим сета для следующей партии
автоматически сбрасывается обратно на DefaultGame.

### Логика теннисного матча (TennisMatchTest)
* **Продолжение матча:** Проверка перехода счета по сетам с 0:0 на 1:0 (матч должен продолжаться).

* **Финальная победа в матче:** Проверка завершения матча при достижении игроком 2 выигранных сетов 
(обработаны сценарии победы при счете 2:0 и 2:1).

## 📋 Логирование

В приложении настроена система логирования на базе **SLF4J** и его реализации **Logback**. Сбор логов ведется
параллельно по двум каналам, консольная и файловая, с базовым уровнем фильтрации `INFO`. 

### Консольный вывод (`ConsoleAppender`)
* Логи дублируются в стандартный поток вывода (`STDOUT`) контейнера сервлетов Tomcat.

### Запись в файл (`FileAppender`)
* Все события системы автоматически сохраняются в текстовый файл по пути: logs/project.log
> ⚠️ **Важное предупреждение:** при каждом перезапуске контекста приложения или рестарте сервера Tomcat старый файл 
логов project.log полностью очищается и перезаписывается с нуля.
